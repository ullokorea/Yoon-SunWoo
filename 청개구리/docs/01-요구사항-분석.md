# Step 1. 요구사항 분석 및 핵심 결정 사항

작성일: 2026-11-20 · 기준 문서: [../개발-프롬프트.md](../개발-프롬프트.md)

## 1. 개발 환경 확인 결과 (2026-11-20)

| 항목 | 상태 | 영향 |
|---|---|---|
| Node.js / npm | **없음** | Expo·Next.js 개발 불가 → 설치 필요 (차단 요소) |
| Docker | 없음 | Supabase 로컬 스택(`supabase start`) 불가 → 대체 DB 전략 필요 |
| PostgreSQL | 없음 | 위와 동일 |
| Python 3.12 | 있음 | 보조 스크립트용 |
| git, winget | 있음 | winget으로 Node 설치 가능 |
| Supabase 프로젝트 키 | 없음 | 운영 DB 연결 불가 → 로컬 임베디드 Postgres 사용 |
| 기상청(공공데이터포털) API 키 | 없음 | 실제 Adapter + Mock Adapter 분리 |
| 카카오맵 / 네이버 지도 키 | 없음 | 지도 보기는 키 입력 전까지 비활성 + 안내 |
| Expo/EAS 푸시 자격증명 | 없음 | 알림은 DB 아웃박스에 기록하는 Mock 발송기 |

없는 키·자격증명은 만들지 않는다. 키가 없으면 해당 기능은 화면에 `MOCK` / `미연동`으로 표시한다.

## 2. 핵심 결정 사항 (기본값 제안)

### D1. 저장소 구조 — npm workspaces 모노레포

```
청개구리/
├─ apps/
│  ├─ mobile/        소비자 앱 (Expo + React Native + TS, Expo Router)
│  └─ web/           Next.js (TS + Tailwind): /owner 점주, /admin 관리자, /api 백엔드
├─ packages/
│  ├─ core/          순수 TS 도메인 로직 (날씨 판정, 할인 엔진, 예약 규칙, QR 토큰) — 테스트 집중
│  ├─ db/            SQL 마이그레이션, 시드, DB 클라이언트
│  └─ design-tokens/ 색상·간격·타이포 토큰 (앱·웹 공유)
└─ docs/
```

점주 관리자와 플랫폼 관리자는 **하나의 Next.js 앱에서 역할별 라우트로 분리**한다. 초기 스타트업이 배포·운영할 대상이 하나 줄고, 권한 검증 코드를 한 곳에서 관리할 수 있다.

### D2. 백엔드 — Next.js API(Route Handlers) + PostgreSQL

- 모든 쓰기 작업(예약, 할인 설정, QR 확인, 승인)은 **API 서버를 통해서만** 수행하고, 서버에서 역할·소유권·가격·수량을 검증한다.
- DB는 PostgreSQL 방언의 SQL 마이그레이션으로 작성한다.
  - **로컬 개발**: Docker가 없으므로 PGlite(WASM으로 동작하는 실제 Postgres)를 사용해 같은 SQL을 그대로 실행한다.
  - **운영**: Supabase(관리형 Postgres)에 같은 마이그레이션을 적용한다. 클라이언트가 DB에 직접 접근할 경우를 대비해 RLS 정책도 마이그레이션에 포함한다(심층 방어).
- 예약 생성은 `SELECT … FOR UPDATE`로 슬롯 행을 잠그는 트랜잭션으로 처리해 동시 예약과 수량 초과를 막는다.

### D3. 인증

- 이메일과 비밀번호 로그인. 비밀번호는 해시(scrypt)로 저장하고, 세션은 서명된 토큰을 사용한다(웹은 httpOnly 쿠키, 앱은 SecureStore).
- 역할은 `consumer` / `owner` / `admin`이며 `user_roles` 테이블에서 관리한다. 관리자 계정은 시드나 CLI로만 만든다(회원가입으로는 생성할 수 없음).
- 추후 Supabase Auth나 카카오 로그인으로 바꿀 수 있도록 인증 모듈을 인터페이스로 분리한다.

### D4. 날씨 판정 — 지역 단위 상태 머신

데이터 소스(실제 Adapter는 키가 있을 때만 동작):
- 기상청 단기예보 조회서비스: 초단기실황(PTY, RN1), 초단기예보, 단기예보
- 기상특보 조회서비스: 태풍·강풍·호우 특보
- 태풍정보 조회서비스: 태풍 진로 예보

지역 단위는 기상청 격자(nx, ny)이며, 매장은 위경도를 격자로 변환해 지역에 매핑한다.

| 상태 | 진입 조건 | 일반 우천 할인 | 태풍 특가 | 신규 방문 예약 |
|---|---|---|---|---|
| `CLEAR` 맑음 | 기본 | 미리보기만 | – | 불가(할인 예약) |
| `RAIN_FORECAST` 비 예보 | 6시간 내 강수확률 ≥ 60% 또는 PTY 예보 | 미리보기·알림 신청 | – | 불가 |
| `RAINING` 비 | 실황 PTY∈{1,2,4,5,6} 또는 RN1 ≥ 0.1mm | **활성** | – | 가능 |
| `TYPHOON_WATCH` 태풍 접근 | 태풍 예상 진로가 72시간 내 영향 + 해당 지역 특보 없음 | 날씨 따름 | 등록·예고, **안전 시간대 및 태풍 이후 방문만** 예약 | 안전 시간대만 |
| `DANGER` 위험 | 태풍·강풍·호우 경보 또는 주의보 발효 | 중단 | 혜택 보관 | **차단** |
| `RECOVERY` 회복 | 특보 해제 후 6시간 경과 + 점주 영업 재개 확인 | 날씨 따름 | 회복 특가 활성 | 가능 |
| `UNKNOWN` 판정 불가 | API 장애로 데이터가 30분 넘게 오래됨 | 신규 활성화 중단 | 태풍 맥락이면 차단 | 보수적으로 제한 |

전환 규칙(깜빡임 방지):
- `RAINING`에 진입하면 **최소 60분 유지**한다. 강수가 없는 관측이 연속 2회(약 1시간) 이어져야 해제한다.
- `DANGER` 진입은 즉시 처리하고(안전 우선), 해제는 특보 해제 후 유예 시간이 지나야 한다.
- 모든 전환은 `store_weather_states` 이력에 판정 근거(관측값, 출처, mock 여부)와 함께 기록한다.
- 확정 예약은 날씨가 바뀌어도 할인 조건을 스냅샷으로 보존한다. `DANGER` 진입 시에는 변경·취소 안내만 보내며 자동 취소하지 않고, 사용자가 선택한다.

### D5. 할인 엔진

- 할인율 범위: 일반 우천 10~30%, 태풍 캠페인(`TYPHOON_WATCH` 사전 예약, `RECOVERY`) 최대 50%. 범위를 벗어나면 서버에서 거부한다.
- 유형: 전체 메뉴 / 특정 메뉴 / 세트 / 시간대 / 선착순(일일 한도)
- 가격은 **서버가 메뉴 정가와 캠페인 규칙으로 계산**한다. 클라이언트가 보낸 가격은 무시하고, 예약 확정 시 `reservation_items`에 정가·할인율·할인가를 스냅샷으로 저장한다.
- 최대 할인 금액과 최소 주문 금액을 적용한다. 원 단위 미만은 내림 처리한다.

### D6. 예약과 QR

- 상태 흐름은 `PENDING`(점주 승인 대기) → `CONFIRMED` → `VISITED`이며, 그 밖에 `CANCELLED_BY_USER`, `CANCELLED_BY_STORE`, `CANCELLED_SAFETY`, `REJECTED`, `NO_SHOW`, `EXPIRED`(승인 지연)가 있다.
- 매장별로 자동 승인 여부를 설정한다. 승인 대기 상태로 30분이 지나면 `EXPIRED`로 바꾸고 슬롯 수량을 복구한다.
- QR은 예약 ID와 무작위 nonce를 HMAC으로 서명한 토큰이다. 서버 비밀키로 검증하며 한 번만 사용할 수 있다(`qr_verifications`에 사용 기록).

### D7. 지도와 알림

- 지도: 먼저 리스트와 거리 표시(하버사인 공식)를 구현한다. 카카오맵 키가 있으면 지도 보기를 활성화하고, 없으면 "지도 미연동" 안내를 표시한다.
- 알림: `notifications` 아웃박스 테이블에 기록하고, 발송기 인터페이스(Expo Push / Mock)로 보낸다. 사용자별 같은 유형의 알림은 3시간에 1회로 제한한다(빈도 제어).

### D8. 시드 데이터

- 시범 지역의 기본값은 **부산 동래구 온천장 일대**다(팀 다른 프로젝트와 같은 지역). 다른 지역을 원하면 바꾼다.
- 시드 매장·메뉴는 모두 가상이며, 이름 앞에 `[샘플]`을 붙이고 개발 모드 배너를 표시해 실제 데이터처럼 보이지 않게 한다.

## 3. 모호한 부분과 처리 방침

| 모호한 점 | 기본 처리 |
|---|---|
| "비 오는 지역"의 판정 단위 | 기상청 5km 격자 단위 |
| 비 예보 단계에서도 예약을 받는가 | 받지 않는다. 알림 신청만 가능 |
| 태풍 접근 단계의 "안전한 방문 시간대" | 특보 발효 예상 시각 6시간 전까지의 슬롯만 허용하고, 그 이후 슬롯은 `RECOVERY` 이후 날짜만 예약 가능 |
| 점주 승인 vs 자동 승인 | 매장별 설정(기본값: 자동 승인) |
| 노쇼 처리 | 방문 시각 30분 후부터 점주가 노쇼로 처리할 수 있음. 제재 정책은 Phase 2 |
| 사업자 인증 | MVP에서는 사업자등록번호 형식 검증 + 관리자 수동 승인. 국세청 진위확인 API는 키가 생기면 연동 |
| 통계의 "추정 추가 매출" | 할인 예약 할인가 합계를 "추정"으로 표시하고, QR 방문 완료분만 "확정 방문"으로 구분 |

## 4. 구현 순서 (Phase 1)

1. `packages/core`: 날씨 상태 머신, 할인 엔진, 예약 규칙, QR 토큰 + 단위 테스트
2. `packages/db`: 스키마, 마이그레이션, RLS, 시드
3. `apps/web` API: 인증, 매장, 할인, 예약, QR, 관리자, 날씨 갱신 작업
4. `apps/web` 점주와 관리자 화면
5. `apps/mobile` 소비자 앱(Expo, 웹 미리보기 포함)
6. 통합 테스트(동시 예약, 수량 초과, 권한 위반, API 장애, 태풍 특보)
